## 4. AI 構成

- **web（公開チャット）**: Gemini Developer API キー（`GEMINI_API_KEY`）。`getModel` が
  キーありなら Developer API、無ければ Vertex に分岐。モデルは `gemini-3.1-flash-lite`。
  **プリペイド残高**が Google 側のハード上限。
- **admin（議事録抽出・要約生成）**: Vertex AI（ADC）。`gemini-2.5-flash/pro` で
  PDF マルチモーダル（議事録→Markdown、議案/会派見解の構造化抽出、議案要約）。
- **多層コスト防御（web）**: ①回数レートリミット（per-IP/per-user、`check_rate_limit`）
  ②アプリ層コスト上限（per-user/system 日次・月次、`chat_usage_events` 集計）
  ③fail-closed ④プリペイド残高（最終ハード上限）

## 5. デプロイ・CI・自動化

- **デプロイ**: `cloudbuild.web.yaml` / `cloudbuild.admin.yaml` を `gcloud builds submit` で**手動**実行（Cloud Run）。`--set-env-vars` でコスト上限/レート/GA等、`--update-secrets` で機密を注入。
- **GitHub Actions**:
  - `sync_teirei.yml`: 毎日10時 JST に大田区議会ページから議案/報告/会派見解を Cloud へ**自動同期**（既存は更新・新規は下書き）
  - `pinact_check` 他（code_check / integration_test は `[main, develop]` トリガーのため `ota/develop` では走らない）
- **要約生成（enrich）**: `packages/seed/main/enrich-bill-summaries.ts` を**手動**実行（Vertex/ADC が必要）。区長提出議案・議員提出議案・報告・その他の PDF から要約生成。
- **マスタ投入**: `seed-cloud-master.ts`（会派/委員会/会期/タグ）

## 6. 開発上の痛み（今回の開発で観測）

> リファクタ・スタック判断の最重要インプット。

1. **GCP 認証の頻繁な失効が最大のボトルネック**
   - `gcloud auth login` / `application-default login` が u-zero Workspace の再認証強制で繰り返し失効。**デプロイ毎・enrich 実行毎**に再認証が必要だった。
2. **GCP の権限・組織まわりの壁**
   - 公開（allUsers）に組織ポリシー緩和が必要、`orgpolicy.policyAdmin` の付与、IAP/課金アカウント権限など、都度ブロック。
3. **デプロイが手動・多段**（gcloud builds submit を都度。DBはdaily syncと別、enrichも別、公開はpublish操作）。
4. **二系統の混在に起因する不整合**（後述のリファクタ候補と重複）。

→ ランタイム（Cloud Run）自体の問題は少なく、**痛みの大半は GCP の認証・権限**に集中。

## 8. スタック選択肢（意思決定用メモ・本書では未決）

すでに **Cloudflare + Supabase** を保有。GCP 依存（特に対話認証）が痛みの中心。

- **A. Cloudflare 全寄せ**: Workers(OpenNext)+Cloudflare Access+Gemini キーのみ。GCP 完全卒業。長期的に最も身軽だが、Next.js on Workers の互換検証（admin の PDF マルチモーダル/Node依存）が必要。
- **B. クイックウィン**: ホスティングは Cloud Run 継続。AI を Gemini キーのみ（ADC卒業）・admin を Cloudflare Access（IAP/組織ポリシー卒業）・デプロイをトークン化。低リスクで痛みの大半を除去。
- **C. 現状維持**: スタックは触らずリファクタのみ先行。

→ 判断材料は「痛み＝GCP認証」「すでにCloudflare/Supabase保有」「移行コスト vs 効果」。
