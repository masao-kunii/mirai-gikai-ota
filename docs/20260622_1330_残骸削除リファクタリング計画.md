# 残骸削除リファクタリング計画（身軽化フェーズ1）

最終更新: 2026-06-22
前提ドキュメント: [20260622_1300_アーキテクチャ現状整理.md](20260622_1300_アーキテクチャ現状整理.md)

## 目的

本家追従を卒業したので、国会版（upstream）由来の残骸と直近使わない機能を削除し、
コードベースを身軽にする。**スタック移行（Cloudflare等）の前に**負債を減らし、
以後の変更を速く・安全にする。

## 方針

- **小さく確実なものから**。PRを分割し、各PRで `lint / typecheck / build / test` を通す。
- 作業は **worktree**（`ota/develop` から分岐）で行う。
- DBテーブルを落とす場合は **drop migration を追加**し、本番適用はユーザーが実行（分類器がブロックするため）。
- **判断が要る箇所は実装前に確認**（特に Phase 3 の波及範囲）。

## Phase 3: interview サブシステム削除（大規模・要スコープ確認）

> **⚠️ ここが最大の意思決定ポイント。** 「interview」単体ではなく、依存する機能群が
> 連鎖削除になる。実装前にスコープを確定する。

### 連鎖する依存（調査結果）

```
interview_* テーブル
  └─ topic_analysis_classifications.interview_report_id  (FK, ON DELETE CASCADE)
  └─ report_reactions                                    (interviewレポートへの反応)
  └─ expert_registrations                                (レポートへの専門家コメント)
  └─ 公開: bill-detail-layout / bill-detail-header からの導線
  └─ 公開: header-client.tsx の nav
```

→ interview を消すと **topic-analysis / report-reaction / experts / 公開レポート閲覧** も一緒に消える。
これは「AIインタビューで住民の声を集めて分析する」サブシステム全体の撤去に相当する。

### 削除対象（スコープ確定後）

- web features: `interview-session` / `interview-config` / `interview-report`（＋ 連鎖: `report-reaction`）
- web routes: `(main)/bills/[id]/interview` / `(main)/preview/bills/[id]/interview` / `api/interview` / `dev/features/interview`
- admin features: `interviews` / `interview-config` / `interview-reports` / `interview-simulation`（＋ 連鎖: `topic-analysis` / `experts`）
- admin routes: `(protected)/interviews` / `(protected)/bills/[id]/interview` / `api/interview-config` / `api/interview-simulation`
- 共通: `interview-links.ts`、routes.ts の interview 関数、header nav、bill-detail の導線
- DB: drop migration（`interview_*` 6テーブル＋2ビュー、連鎖で `topic_analysis_*` / `report_reactions` / `expert_registrations` / `interview_session_ratings`）
- 関連: `DEFAULT_INTERVIEW_CHAT_MODEL`、interview関連の env / cloudbuild 設定

### スコープの選択肢（**ユーザー確認事項**）

- **A. 完全削除**: コード＋テーブル全部消す。最も身軽。データ復元不可。
- **B. UI/導線だけ撤去**（コード・テーブルは残す）: 可逆。今は隠すが将来再開可。差分小。
- **C. 段階削除**: まず導線・nav・公開ルートを撤去（B）→ 落ち着いてからコード／テーブルを削除（A）。

> 規模が大きく連鎖も広いので、**まず C（導線撤去）から入り、問題なければコード・DBを落とす**のを推奨。
> 「直近使わない」が「将来も使わない」かで A/B が分かれる。

### PR分割案（Aの場合）

1. 公開導線・nav・routes の撤去（ユーザー影響を先に止める）
2. web interview features 削除
3. admin interview features ＋ topic-analysis/experts 削除
4. drop migration（本番適用はユーザー）
