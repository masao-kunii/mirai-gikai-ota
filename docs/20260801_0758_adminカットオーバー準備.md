**旧 `admin/`（Next.js / Cloud Run）を停止して apps/admin に切り替える**までに必要な作業を、

前提となる設計は [TARGET_ARCHITECTURE](TARGET_ARCHITECTURE.md) Phase 4 と
[ADR 0002（Workers デプロイ）](adr/0002-workers-deploy.md) / [ADR 0003（IaC）](adr/0003-iac-terraform.md)。

## 1. 決定事項（2026-08-01 決定済み）

### 1-1. 管理者の認可モデル → **A: Access のポリシーのみ**
Access のポリシー（許可メールアドレス / Google Workspace グループ）で管理者を管理し、
**アプリ側に管理者テーブルを持たない**。

- 現状の api 実装がそのまま該当する（`requireAdminAccess` は Access JWT を JWKS 検証し、
  通ったリクエストを `app_admin` として扱う。アプリ側の role 判定は持たない）。**実装変更は不要**。
- 帰結: 旧 `admins` 機能（476 LOC）は **移行不要**。
- 運用上の含意: **管理者の追加・削除は Cloudflare Zero Trust のポリシー変更で行う**
  （アプリ内に管理者管理画面はない）。誰が管理者かの一覧も Zero Trust 側が正となる。

### 1-2. 議案サムネイル画像 → **当面なしで運用**
R2 等の画像基盤は用意せず、サムネイルなしで運用する。
必要になった時点で「R2 バケット＋公開 URL 設計＋アップロード経路」を別途設計する
（それまでは公開サイト側はサムネイル未設定として描画される既存挙動のまま）。

### 1-3. 旧 admin の停止時期 → **切り替え後に停止**
新 admin へ切り替えて受け入れ確認が済んだのち、旧 admin（Cloud Run）を停止する。
切り替え前に未移行機能を作り込むことはしない（1-1・1-2 の決定により未移行は実質なし）。

> この3点が決まったため、**カットオーバーに残るのはインフラ作業（§2-1〜2-4）のみ**。

## 2. 作るもの（実装・設定）

### 2-1. apps/admin のデプロイ経路（必須）
現状 `apps/admin` は Vite の静的 SPA だが、デプロイ設定がない。方針の候補:

- **A. Workers Static Assets（推奨）**
  `apps/admin/wrangler.jsonc` を追加し、`dist/` を assets として配信する Worker
  （例 `mirai-gikai-admin`）を作る。`package.json` に `build:cf` / `deploy` を追加。
  SPA なので `not_found_handling: "single-page-application"` を指定する。
- B. Cloudflare Pages に載せる（Workers と管理が二重になるので非推奨）

**API の呼び先**: SPA は相対 `/api` を叩く実装。したがって
**admin と api を同一オリジンに載せる**必要がある（下記 2-2）。

### 2-2. ドメインとルーティング（必須）
管理画面は公開サイトと**別ドメイン／別サブドメイン**にし、Access をそのホストに掛ける。
例: `admin.ota.aix.tokyo`

- `admin.ota.aix.tokyo/*` → `mirai-gikai-admin`（SPA）
- `admin.ota.aix.tokyo/api/*` → `mirai-gikai-api`（**公開サイトと同じ api Worker**）

Routes は Cloudflare ダッシュボード、または `infra/`（Terraform）に定義を追加して管理する。

> 注意: `/api/admin/*` は Access の背後に置く必要があるが、**公開サイト側の `/api/*`（チャット・インタビュー等）は Access を掛けてはいけない**。
> そのため「**管理用ホスト全体に Access を掛け、公開ホストには掛けない**」構成にする。api Worker 自体は共用でよい（`requireAdminAccess` が `/api/admin/*` のみに適用されるため）。

### 2-3. Cloudflare Access アプリ（必須）
Zero Trust で以下を作る:

1. **Access Application** を `admin.ota.aix.tokyo` に作成（Self-hosted）
2. **Identity provider** に Google を設定
3. **Policy** で許可対象（管理者）を指定。**ここが唯一の管理者管理**（§1-1 A）なので、
   運用担当のメールアドレス、または Google Workspace グループを登録する
4. 発行された **Application Audience (AUD) タグ** を控える
5. **Team domain**（`https://<team>.cloudflareaccess.com`）を控える

### 2-4. api への環境変数（必須）
```bash
# apps/api で実行（値は 2-3 で控えたもの）
npx wrangler secret put CF_ACCESS_TEAM_DOMAIN   # https://<team>.cloudflareaccess.com
npx wrangler secret put CF_ACCESS_AUD           # Application Audience (AUD) タグ
```
未設定のままだと `/api/admin/*` は **500（フェイルクローズ）** で誰も通れない。
逆に、この2つを設定して初めて管理画面が使えるようになる。

> `ADMIN_AUTH_DEV_BYPASS` は**本番では絶対に設定しない**（ローカル開発専用）。

### 2-5. AI 機能の前提（確認）
`/bill-contents/:id` の AI 生成と `/bills-extract` の議事録抽出は
**Vertex AI（`gemini-2.5-pro`）** を使う。api Worker から Vertex を呼べること
（サービスアカウント／認証情報、対象モデルの有効化）を確認する。

> 補足: Gemini Developer API キー（`GEMINI_API_KEY`）は公開チャット用のコスト天井として設定しているが、
> **2.5-pro は Developer API では新規利用不可**のため、管理系の AI 生成は Vertex 経路である必要がある。

## 3. 実行手順（順序）

```text
1. ✅ 意思決定（§1: A / サムネイルなし / 切り替え後に停止）      ← 2026-08-01 完了
2. ✅ apps/admin に wrangler 設定と deploy スクリプトを追加（§2-1） ← PR #143
3. admin 用サブドメインを用意し、Routes を設定（§2-2）
4. Zero Trust で Access アプリ＋ポリシーを作成（§2-3）
5. api に CF_ACCESS_TEAM_DOMAIN / CF_ACCESS_AUD を設定（§2-4）
6. apps/admin をデプロイ → Access のログインを通って画面が開くことを確認
7. 受け入れ確認（§4）
8. 旧 admin（Cloud Run）を停止、社内リンク・ブックマークを新 URL へ切り替え
```

ロールバックは各段で容易:
- 6 で問題 → Access ポリシーを緩めるか、Routes を戻す（旧 admin は生きている）
- 8 の後で問題 → Cloud Run を再起動すれば旧 admin に戻せる（DB は共通）

## 4. 受け入れ確認（切り替え前チェックリスト）

実データ（本番 DB）に対して、新 admin で以下が一通りできることを確認する。

- [ ] Access のログインを経て管理画面が開く／許可外のアカウントは弾かれる
- [ ] 議案: 作成・編集（審議状況/公開状態）・タグ・会派スタンス・本文編集
- [ ] 議案: **公開状態を published にすると公開サイトへ反映**される
- [ ] 議案: 一括取り込み（定例会ページ）→ 下書きで作成される
- [ ] 議事録: 作成・本文（Markdown）編集
- [ ] インタビュー設定: 受付中／終了の切り替えが公開サイトに反映される
- [ ] 審査キュー: 承認で公開される／却下で非公開になる
- [ ] 通報: 一覧表示と非公開化
- [ ] マスタ: タグ・会派・委員会・会期の編集
- [ ] AI: 議案本文の生成／議事録からの抽出（Vertex 経路で成功する）
- [ ] 管理者の追加・削除が **Zero Trust のポリシー変更**で効く（§1-1 A の運用確認）

## 5. 切り替え後に残るもの

決定（§1）により、切り替え前にやることは無くなった。切り替え後に必要が生じたら着手する。

| 項目 | 対応 |
|---|---|
| 議案サムネイル画像 | 必要になったら R2 バケット＋公開 URL 設計＋アップロード経路を設計して追加（§1-2） |
| 速報版（sokuhou）からの取込 | 定例会ページ取込（#142）の実運用を見てから判断 |
| 旧 admin（Cloud Run）の停止 | 受け入れ確認後に停止。しばらくは戻せる状態で置いておく（DB は共通のため再起動で復帰可） |
| MCP ツール | 新アーキで必要かは別途判断 |

## 6. 運用メモ（切り替え後）
- **管理者の追加・削除は Cloudflare Zero Trust の Access ポリシーで行う**。アプリ内に管理者管理画面はない（§1-1 A）。
- 管理画面は Access の背後にあるため、**社内リンク・ブックマークは新 URL（admin サブドメイン）へ差し替える**。
- `ADMIN_AUTH_DEV_BYPASS` はローカル専用。本番 Worker に設定されていないことを定期的に確認する。
