## 0. プロダクトビジョン（すべての機能判断の基準）

**地方自治体における政治・自治を住民に伝え、住民の声を拾って可視化し、双方向のフィードバックによって住民が政治参加できるデジタル民主主義基盤をつくる。**

- 国政と地方自治は政治形態が異なる。二元代表制・委員会中心の区議会の実態（議案・会派見解・議決・請願陳情）を、住民が理解できる形に翻訳して届ける。
- 「伝える」（議案の平易化・AI チャット）と「聴く」（インタビュー・意見公開・論点集約）は両輪。集めた声は**公開・可視化**が出口である。
- 本家みらい議会（国会版）とは訣別済み。コード互換性は考慮しない。

## 0.5 最重要原則（すべての技術判断の基準）

1. **検証器ファースト**: 正しさを人間や AI の注意力に頼らず、機械検証（型・DB 権限・lint・CI）に変換する。「規約」を見つけたら「検証器」にできないか常に考える。
2. **低マジック**: 挙動はすべてコードのテキストに現れること。暗黙のキャッシュ、実行時メタプログラミング、規約ベースの暗黙配線を導入しない。冗長で明示的な方を選ぶ。
3. **公開境界の多重防御**: このプロダクトの守るべき境界はテナント間ではなく「公開してよいもの／まだ公開していないもの／住民個人の声」の間にある。境界をアプリロジックだけに依存させず、DB ロール・RLS・型で多重化する。
4. **テキストの外に真実を置かない**: インフラ設定・DB ポリシー・運用手順は、すべてリポジトリ内のコード／ドキュメントとして管理する。ダッシュボードでの手動設定を残さない。
5. **expand/contract**: 破壊的変更は「後方互換の追加 → 移行 → 旧の削除」の3段階で行う。一発の破壊的変更をしない。

## 0.6 プロダクト特性がアーキテクチャに課す制約

| 特性 | 帰結 |
|---|---|
| 主戦場は**匿名住民の閲覧**（議案・会期・会派見解） | SEO / OGP は生命線。SSR または事前レンダリングが必須。認証はむしろ例外側 |
| 書き込みは2種のみ: 管理者の編集（実質1人）と住民の声（匿名） | エンタープライズ認証（SSO/SCIM）は不要。認証の作り込みを最小化する |
| 心臓部は**データパイプライン**（区議会サイト → 取得 → AI 平易化 → DB） | Web アプリより ETL としての規律（冪等・再処理可能・ソース保存）が重要 |
| 運営は**一人 + AI エージェント** | 認知負荷と月額固定費を最小に。検証器が人手レビューの代替。運用手順は全てコード化 |
| 住民の声を預かる | 同意・匿名性・モデレーション・透明性は機能ではなく原則（§9） |
| マルチ自治体は将来の可能性（当面やらない） | 自治体固有部を局所化するに留める（§4.4）。スキーマの多テナント化は今はしない |

- どちらか迷う処理はユーザーに確認する

## 2. データモデル

### 2.1 基本方針
- **単一自治体（大田区）**。`organization_id` は導入しない。理由: 自治体ごとにデータソースの構造が全く異なり共通スキーマ化の仮説を今は検証できない。将来必要になれば expand/contract で追加できる（全行 = 大田区でバックフィル可能）。
- データは3階級に分ける。この区別がセキュリティモデル（§3）の土台になる:

| 階級 | 例 | 誰が読めるか |
|---|---|---|
| **公開データ** | published な議案・会期・会派見解・公開レポート・論点集約 | 全員（匿名） |
| **未公開データ** | draft 議案・AI 生成下書き・取り込みログ | 管理者のみ |
| **住民の声（個人スコープ）** | interview セッション・メッセージ・未公開レポート・リアクション | 本人と管理者のみ |

### 2.2 事実と生成物の分離
- **一次事実**（区議会サイト由来: 議案番号・件名・議決結果・会派態度）と **AI 生成物**（平易な要約・タイトル・論点集約）はカラム／テーブルを分離し、AI 生成物から一次事実を上書きしない。
- AI 生成物には生成メタデータ（モデル・生成日時）を保持し、公開画面で AI 生成であることを表示できるようにする（§9.3）。

## 3. 公開境界セキュリティ（このプロダクトの背骨）

汎用 SaaS における「テナント分離 RLS」に相当する位置に、本プロダクトでは「公開境界」を置く。

### 3.1 DB ロールの分離（構造的な多重防御）
DB 接続ロールを用途で分け、公開系 API から未公開データへ**構造的に**到達できなくする:

| ロール | 権限 | 使用者 |
|---|---|---|
| `public_reader` | 公開データのみ SELECT（RLS: `publish_status = 'published'` 等） | 公開ページ・公開 API の読み取りパス |
| `resident_writer` | 住民の声テーブルのみ INSERT/SELECT/UPDATE（自分の匿名 ID の行に限定） | interview・チャット・リアクション |
| `app_admin` | 全テーブル読み書き（RLS 免除しない。FORCE RLS + 明示ポリシー） | 管理 API・sync パイプライン |
| `migrator` | DDL。アプリからは使用しない | マイグレーションのみ |

- 公開 API ハンドラが誤って draft を返すバグを書いても、`public_reader` 接続では**行が存在しない**。これが多重防御の中核。
- ポリシー・GRANT はすべて Drizzle マイグレーション内の SQL としてリポジトリ管理する。ダッシュボードで直接触らない。
- アプリの接続ユーザーをテーブルオーナー・スーパーユーザーにしない（RLS バイパス防止）。

### 3.2 住民の匿名コンテキストの注入
- 住民の声への行アクセス制御が RLS に依存する箇所では、**素の `SET` を禁止し、必ずトランザクション内で `set_config(..., true)`（SET LOCAL 相当）** を使う。接続プールでの文脈残留は住民の声の漏洩事故になる。

```ts
await db.transaction(async (tx) => {
  await tx.execute(sql`SELECT set_config('app.anon_id', ${anonId}, true)`)
  // このトランザクション内でのみ住民スコープの読み書きを行う
})
```

### 3.3 ストリーミング例外（重要）
- チャット等の SSE ストリーミング応答中に DB トランザクション（＝接続）を保持してはならない。
- ストリーミング系ハンドラは「開始前の短いトランザクション（検証・読み取り）→ 接続を返却してストリーム → 完了後の短いトランザクション（使用量記録等）」の3分割を規約とする。

## 4. 認証・認可

### 4.1 管理者
- **Cloudflare Access**（Zero Trust）で管理ドメイン全体を保護する。Google IdP（`app.masao-kunii.jp`）連携。現行の Cloud IAP と同型のパターンで、Workers 移行後の置き換え先。
- アプリコード側は Access の JWT アサーションを検証するミドルウェア1枚のみ。**ログイン・セッション管理を自作しない。**
- 管理者が増えたときの権限差（例: 編集者/閲覧者）が必要になるまで RBAC を作らない。必要になったら ADR を書く。

### 4.2 住民（匿名）
- アカウント登録を要求しない。**署名付き（HMAC）匿名 ID クッキー**を初回訪問時に発行し、interview・リアクション・レート制限の主体とする。
- 匿名 ID に個人特定情報を一切ひもづけない（§9.1）。クッキー削除＝別人になることを許容する（デジタル民主主義としてはそれが正しい既定値）。
- JWT を権限トークンとして使わない。匿名 ID は「識別子」であって「権限の主張」を含まない。

### 4.3 AI エージェント・MCP
- エージェントは管理者の委任を受けた principal として扱い、**人間管理者以上の権限を持たせない**。RLS/ロールを迂回する万能サービスアカウントを作らない。
- 管理 MCP ツール（bills-tools 等）の書き込み・破壊的操作は human-in-the-loop（確認ゲート）を維持する。
- 監査可能性: 管理系の書き込みには「誰（人間/エージェント）がいつ」を記録する。

## 5. 公開フロントエンド（SEO / OGP は生命線）

- 「大田区 補聴器 条例」で議案ページが検索上位に出ること、SNS シェアで OGP が展開されることは、このサイトの存在意義そのもの。**素の SPA は禁止**。
- **TanStack Start による SSR** を第一候補とする。選定理由: (a) SSR で SEO/OGP を解決 (b) TanStack Router の型安全ルーティングは検証器ファーストに合致 (c) Next.js App Router 系の暗黙キャッシュ・暗黙境界がなく、loader/server function が明示的（低マジック原則との両立）。
- フォールバック案（Phase 3 開始時に成熟度を再評価して ADR で確定）: sync 駆動のプリレンダ（議案は日次更新なので、sync 後に静的再生成する構成は本質的に相性が良い）。
- キャッシュは Cloudflare CDN レイヤで明示的に制御する（`Cache-Control` をコードに書く）。フレームワークの暗黙キャッシュ機構に依存しない。

## 6. API 設計（Hono RPC）

- ルートは機能ドメインごとに分割し、単一の巨大な `AppType` を作らない。クライアント（`hc`）もドメインごとに分割し、サーバーのルート型は明示的に export した確定済み型を import する。
- 入力は必ず zod スキーマで検証する。スキーマから TS 型を導出し、二重定義しない。
- Hono RPC は第一者クライアント（公開 web・管理 SPA）専用。外部公開 API が必要になったら `@hono/zod-openapi` で別契約を切る。
- `c.get('session')` / `c.get('db')` 等は Hono の `Variables` として型定義し、型なしアクセスを禁止する。
- **公開ドメインのハンドラでは `public_reader` 接続のみ**、管理ドメインでは `app_admin` 接続のみを使用可能とし、lint（import 制限）で機械的に強制する。
- デプロイ順序は API → フロントの順を厳守（後方互換を保つ）。

## 7. 意図的に導入しないもの（YAGNI リスト）

必要になった時に ADR を書いてから導入する。先回りで作らない:

- マルチテナント（`organization_id`・テナント文脈注入）
- WorkOS 等の IdP SaaS、SSO/SCIM、住民アカウント登録
- Redis / セッションストア（管理者は Cloudflare Access、住民は署名クッキーで足りる）
- ジョブキュー（Cloudflare Queues / BullMQ）。GitHub Actions cron で足りている間は持たない
- RBAC（管理者が実質1人の間）
- マイクロサービス分割・GraphQL・イベントソーシング

## 8. データパイプライン（sync）の設計原則

区議会サイト → 取り込み → AI 平易化 → 公開、の流れはこのプロダクトの心臓であり、ETL としての規律を課す:

1. **冪等**: 何度実行しても同じ結果（upsert 基本）。日次 cron と手動再実行が常に安全であること。
2. **ソースの保存**: 取得した HTML / PDF は取得日時付きで R2 に保存する（区サイトの改編・削除に備えた再処理可能性と、一次事実の証跡）。
3. **事実が先、生成は後**: 一次事実の取り込みと AI 生成は別ステップ。AI 生成の失敗が事実データの取り込みを止めない。
4. **警告の可視化**: 照合失敗・スキップは必ず警告としてログに出し、件数を実行サマリに含める（「静かなスキップ」が補聴器条例の会派見解欠落を3週間隠した教訓）。警告が出た場合に通知する仕組みを持つ。
5. **自治体固有部の局所化**: 大田区サイトのパーサ・URL 構造は `adapter` 層に隔離する。マルチ自治体をやる場合の拡張点はここだけにする（スキーマではなくアダプタで吸収する）。

## 9. 住民の声の取り扱い原則（デジタル民主主義の信頼基盤）

機能仕様ではなく**原則**である。これに反する実装・仕様変更はユーザー確認なしに行ってはならない。

1. **同意なき公開なし**: 住民の声は本人の明示同意（`is_public_by_user`）なしに公開しない。
2. **匿名性の保護**: 声に個人特定情報をひもづけない。公開レポートから発言者個人を特定できる情報を求めない・保存しない。
3. **AI の透明性**: AI が生成・要約・集約したコンテンツにはその旨を表示する。論点集約は元の声（公開レポート）へ遡及できるリンクを保つ。
4. **安全ゲート**: 公開前にモデレーション（自動スコア + 閾値）を通す。境界例の最終判断は人間が行う。
5. **少数意見の保護**: 集約・可視化は多数派要約に還元しない。論点ごとに多様なスタンスの代表意見を保持する。
6. **フィードバックの環**: 声の可視化は議会の動き（会派見解・議決結果）と同じ画面文脈で提示し、「声を上げる → 議会がどう動いたかを見る」の往復を設計の中心に置く。

## 10. 検証器（テスト・lint・CI）

### 10.1 必須テスト: 公開境界漏洩テスト
- **CI に常設。** `public_reader` 接続から: (a) draft 議案・未公開レポート・管理系テーブルの SELECT が 0 件/拒否になること (b) あらゆる INSERT/UPDATE/DELETE が拒否されること、を検証する。
- `resident_writer` 接続から: 他人の匿名 ID のセッション・メッセージ・レポートに読み書きできないことを検証する。
- Drizzle スキーマからテーブル一覧を機械的に列挙し、**新テーブル追加時に自動でテスト対象が増える**構造にする。各テーブルには「公開/未公開/住民スコープ」の分類をスキーマ定義側で宣言させ、分類漏れ自体をテストで検出する。
- `pg_policies` を引いて、全テーブルに想定どおりのポリシーが存在することを検証するテストを併設する。

### 10.2 テスト環境
- testcontainers 等で本物の Postgres を使う。RLS・GRANT はモックで検証しない。
- 現実的なシード: 「published/draft 混在の議案・会派見解・複数の匿名住民の声」を1コマンドで構築できるファクトリを整備する。published のみのデータでの動作確認を検証完了と見なさない。

### 10.3 lint による規約の機械化
- 公開ドメインのハンドラ層で `app_admin` 接続の import を禁止（§6）。
- `BillId` / `SessionId` / `AnonId` 等の ID は branded type とし、取り違えを型エラーにする。
- ストリーミングハンドラでのトランザクション保持（§3.3）をレビュー観点として明文化し、可能ならカスタムルール化する。

### 10.4 CI パイプライン（最低限）
1. `tsc --noEmit`（strict）
2. Biome（format + lint）
3. vitest（単体 + 公開境界漏洩テスト）
4. マイグレーションの forward 適用検証
5. Playwright smoke（主要公開ページ + チャット疎通。現行資産を流用）
6. **AI コストの月次上限アラート**（chat_usage_events 集計。個人運営の生命線）

### 10.5 観測性
- 全ログに「リクエスト ID・ルート・匿名 ID（ハッシュ）・AI 使用量」を付与する。
- 「チャットだけ遅い/高い」「sync が静かに劣化」を即座に切り分けられることを運用の前提とする。

```
├── docs/
│   ├── adr/            # 意思決定記録
│   └── TARGET_ARCHITECTURE.md   # 本書
└── (web/ admin/ packages/ ほか現行コード)   # 移行完了まで並存 → 段階削除
```

- `apps/web`・`apps/admin` から `apps/api` へは**型のみ**の依存とする（ランタイムコードを import しない）。

## 12. 移行戦略

**ビッグバン書き換えを禁止する。** 実態は「リファクタ」ではなく**新築＋データ共有＋機能移植**である（フレームワーク・ORM・認証・ランタイムが全て変わる）。旧アプリをカットオーバーまで動かし続け、各フェーズ完了ごとにユーザーの確認を得る。

### Phase 0: 現状調査と本書の確定
- 現状（スタック・デプロイ・公開境界の実態＝service_role 一本・認証・sync）を `docs/adr/0001-current-state.md` にまとめ、本書とのギャップ一覧とリスク順の移行提案をユーザーにレビューしてもらう。
- 本書からの逸脱・重要判断は都度 ADR に記録する（TanStack Start 採否、DB ホスト等）。

### Phase 1: 検証器の導入（コードを変えずに網を張る）
- TypeScript strict / `noUncheckedIndexedAccess` の全面化、CI 強化。現行の integration CI・E2E は資産としてそのまま維持する。
- この段階ではアプリの挙動を変えない。

### Phase 2: 新基盤の並走開始（DB は現行を共有）
- `packages/db` を現行スキーマの introspect から作成（**スキーマ変更なし**で開始するのが要点。新旧アプリが同じ Supabase Postgres を見る）。
- DB ロール分離（`public_reader` / `resident_writer` / `app_admin`）と公開境界 RLS を導入。**現行アプリの動作は変えず、多重防御を先に足す。**
- 公開境界漏洩テストを CI に追加してから次へ進む。
- `apps/api`（Hono）で公開読み取り API を新設。

### Phase 3: 公開 web の新築・切替
- TanStack Start で公開サイトを新築（プレビュードメインで並走）。SEO/OGP/構造化データを現行同等以上にしてから DNS 切替。ロールバックは DNS 戻し。
- 現行 E2E スモークを新サイトに向けて流用し、合格をカットオーバー条件とする。

### Phase 4: パイプラインと管理の移植
- sync を `packages/pipeline` + Drizzle へ移植（GitHub Actions 実行は継続）。ソース保存（R2）を追加。
- admin を機能単位のストラングラーで `apps/admin` へ（議案編集 → 取り込み管理 → interview 管理）。Cloudflare Access 化、IAP 廃止。

### Phase 5: 仕上げ
- 旧 Next.js アプリ・Supabase Auth/Storage 依存の削除。IaC 完成。
- DB ホストの再評価（Supabase 継続 vs Neon 等）を ADR で判断。素の Postgres 扱いを貫いていれば dump/restore で移行可能な状態になっている。

### 各フェーズ共通ルール
- expand/contract 厳守。ロールバック手順を常に確保する。
- フェーズ完了ごとにユーザーの確認を得る。

## 13. 禁止事項（明示的な NG リスト）

- 公開ドメインのハンドラからの `app_admin` 接続使用
- `published` 条件を通らない公開応答（公開クエリは必ず公開スコープのヘルパー/ロール経由）
- 素の `SET` によるセッション変数設定（必ず `set_config(..., true)`）
- SSE ストリーミング中の DB トランザクション保持
- Next.js の新規導入（移行完了までの旧アプリ保守を除く）
- 素の SPA での公開ページ配信（SEO/OGP を壊す）
- 住民の匿名 ID への個人特定情報のひもづけ
- 同意のない住民の声の公開、AI 生成コンテンツの無表示公開
- RLS ポリシー・ロール分離なしでの新テーブル追加（分類宣言必須。§10.1）
- ダッシュボード手動設定のみで完結するインフラ変更
- ビッグバン書き換え、一発の破壊的マイグレーション
- エージェント用の RLS/ロール迂回経路の作成
- リクエスト内での重い同期処理（スクレイピング・PDF・一括 AI 生成）
